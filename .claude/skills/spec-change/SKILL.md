# SPEC 개정 절차

`SPEC.md` 는 이 프로젝트의 설계 명세이며 코드보다 상위 권위다. 서두에 "이 문서와 프롬프트가 충돌하면 작업을
멈추고 보고할 것"이라 적혀 있고, 1.1 → 1.5 까지의 개정은 전부 "미결 항목을 근거와 함께 확정"하는 방식으로
쌓였다. 이 절차는 그 방식을 그대로 잇는다. **결정만 적고 근거를 빼면 다음 세션이 그 결정을 뒤집는다** — 이 문서의
모든 규칙은 그 한 가지 실패를 막기 위한 것이다.

## 1. 영향 절 식별

1. `grep -nE '^#{2,3} ' SPEC.md` 로 목차를 뽑고, 요청이 닿는 절을 고른다
2. 코드·테스트·fixture 가 그 절을 어떻게 인용하는지 찾는다:
   ```bash
   grep -rn "SPEC [0-9.]*절\|[0-9.]*절" src/ tests/ scripts/ .github/ | grep -v "^Binary"
   ```
   이 결과가 "SPEC 을 바꾸면 같이 바꿔야 할 파일 목록"의 출발점이다
3. `tests/fixtures/README.md` 의 "고정된 규약" 절과 대조한다. README 는 SPEC 의 규칙을 fixture 값으로 번역한 문서라, SPEC 이 바뀌면 거의 항상 README 도 바뀐다

## 2. 고정 결정 대조

결정들이다. 요청이 이 중 하나에 닿으면 **개정안을 만들지 말고 리더에게 "고정 항목 충돌"로 보고**한다.

## 3. 개정안 작성 규약

SPEC 의 기존 개정 스타일을 그대로 따른다. v1.5 헤더를 보라:

```markdown
*버전: 1.5 / 최종 수정: 2026-09-08*

> **1.5 변경**: 국내 bigram 자카드 임계값 **`0.45` → `0.35` 확정**(6절).
> 국내 발행 자격 = 클러스터 크기 2 이상 명문화(6절) — fixture 의 "국내 3건" 이 전제하던 규칙.
> 1.4가 "fixture 실측과의 불일치"로 남겨 둔 미확정 항목을, 실측 재현 구간
> `0.125 < T ≤ 0.40` 의 중앙값으로 닫았다 — 근거 표는 6절에 있다.
> ...
```

규약:

| 항목 | 규칙 | 이유 |
|------|------|------|
| 버전 | 소수점 둘째 자리 +1 (1.5 → 1.6). 한 세션의 확정 묶음이 한 버전 | 개정 단위 = 결정 묶음. 커밋 단위와 맞춘다 |
| 헤더 줄 | `*버전: X.Y / 최종 수정: YYYY-MM-DD*` 갱신 | |
| 변경 블록 | 기존 블록들 **위에** `> **X.Y 변경**: ...` 인용 블록 추가. 바뀐 절 번호를 괄호로, 옛 값 → 새 값을 굵게, 근거를 한 문장 이상 | 헤더만 읽어도 무엇이 왜 바뀌었는지 보인다 |
| 대체 관계 | 이전 버전의 결정을 뒤집을 때는 "1.2 의 X 결정을 **대체**한다"고 쓰고, 이전 결정이 감수하던 위험이 어떻게 해소됐는지 적는다 (v1.3 앵커 URL 사례) | 뒤집힌 이유가 없으면 다시 뒤집힌다 |
| 무효화 | 기준 자체가 사라진 값은 "무효" 라고 명시한다 (v1.4: "명사 집합 임계값 0.5 는 무효") | 옛 값이 코드 어딘가에 살아남는 것을 막는다 |
| 절 번호 | 움직이지 않는다. 새 절은 `6.5` 처럼 소수점 삽입 | 위 고정 결정 |
| 본문 갱신 | 해당 절의 표·문장을 고친다. 변경 블록만 추가하고 본문을 안 고치면 안 된다 | 본문이 최종 상태여야 한다. 헤더는 이력이다 |
| 상호 참조 | 다른 절이 옛 값을 인용하면 같이 고친다 (`grep -n "0.45" SPEC.md` 식으로 옛 값을 전부 찾는다) | |
| 외부 사실 | 모델 ID·문자 수·엔드포인트는 "(YYYY-MM-DD 확인)" 과 출처 종류(공식 문서/실측/실조회)를 붙인다. 11절의 "확인 완료" 날짜도 갱신 | SPEC 11절이 요구하는 재확인 주기의 기준점 |
| 근거 표 | 수치 결정(임계값, 가중치)은 실측 표를 절 안에 남긴다 (v1.5 6절 방식) | 다음 튜닝이 같은 표를 확장한다 |
| 어조 | "왜"를 적는다. 금지 규칙에는 무너지는 것을 함께 적는다 | 이 문서 전체의 스타일 |

## 6. drift 감사 모드

"SPEC 이랑 코드 맞는지" 류 요청. 개정이 아니라 대조다.

1. 1절 grep 으로 절 참조 목록을 만든다
2. 참조마다 SPEC 본문의 현재 규칙과 코드의 현재 동작을 한 줄씩 대조한다 (값, 순서, 키 이름)
3. `tests/fixtures/README.md` "고정된 규약" 각 항목이 SPEC 어느 절에 근거하는지, 근거가 아직 유효한지 확인
4. 11절 "확인 완료" 날짜가 한 달 이상 지났으면 ops 에게 재확인 요청 항목으로 넘긴다
5. 결과를 `일치 / 불일치(어느 쪽이 맞는지 SPEC 근거) / SPEC 이 모호` 세 분류로 리포트. 모호 항목은 "미결 항목"으로 정리해 다음 개정 후보로 둔다
